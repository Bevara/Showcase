Play an FLV file using the <video> tag

FLV is the container Flash used, and what most FLV files in the wild hold is not the H.264 and AAC that RTMP carries today but the codecs Flash shipped with: Sorenson H.263 for the picture and MP3 for the sound. This file is one of those. flvdmx_1 walks the tag stream and emits one pid per track with the codec named — the picture size read from the Sorenson picture header, the sampling rate from the MP3 frame header, since the tag's own 2-bit rate field cannot say 48 kHz. ffmpeg-h26x_1 decodes the video (Sorenson H.263 is a variant of H.263, and adds 3 Ko to the module), libx264_1 re-encodes it, and isobmff_1 writes the MP4 the <video> element plays. All 1116 frames come out.

The video is played progressively: it starts within a few seconds, while the rest is still being transcoded, instead of after the whole file. The picture and the sound are cut into MP4 segments fed to the element through Media Source Extensions as they are produced. MSE does not take MP3 inside MP4, so the sound goes through libmad_1 and libopusenc_1 to Opus. A browser that cannot do it falls back to decoding the whole file; the line under the player says which way it went.

Code snippet

<video is="universal-video_1" src="ocean.flv" using="mm_solver_1.0.6"
        with="flvdmx_1;ffmpeg-h26x_1;isobmff_1;libx264_1;libmad_1;libopusenc_1" progressive controls> </video>

Without progressive, the whole file is transcoded first and the MP3 is stored as it is: with="flvdmx_1;ffmpeg-h26x_1;isobmff_1;libx264_1" is enough, and the audio in the output is bit-identical to the source.

The same demultiplexer handles the other FLV flavour, AVC with AAC, which then goes through h264bsd_1 instead: with="flvdmx_1;h264bsd_1;isobmff_1;libx264_1". VP6, Screen Video and Nellymoser have no decoder here and are skipped with a warning.
